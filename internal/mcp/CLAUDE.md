# package mcp

JSON-RPC 2.0 Model Context Protocol server exposing Rick's workflow, job, workspace, Jira, wave, observability, and Confluence capabilities to MCP clients (Claude Desktop, Cursor, the agent UI) over stdio and HTTP. **18 tools total.**

The surface is aggressively consolidated to keep the LLM's tool-selection context small. **Facade** tools multiplex over the fine-grained handlers via a flat `include` list or `action` enum — the underlying handlers (`toolWorkflowStatus`, `toolListWorkflows`, `toolWavePlan`, …) remain the single source of truth and are only dispatched to. See `tools_consolidated.go`. When adding any behavior, extend a facade (a new `action`/`include` value) rather than registering a new top-level tool. `TestToolsList` (server_test.go) asserts the exact 18-tool set and that folded names are NOT registered standalone — it is the regrowth guard, so adding a tool is a deliberate edit there, not a silent addition.

The 18 tools:
- **Workflow** — `rick_run_workflow` (launch; `dag=plan-btu`+`page_id` routes to the BTU planner), `rick_workflow_inspect` (read), `rick_workflow_control` (act).
- **Jobs** — `rick_consult`, `rick_run` (launch), `rick_job_inspect` (read), `rick_job_cancel` (the lone mutating job verb, kept standalone so inspect stays read-only).
- **Workspace / wave / diff** — `rick_workspace`, `rick_wave_manager`, `rick_diff_viewer`.
- **Jira** — `rick_jira_read`, `rick_jira_write`, `rick_jira_search`, `rick_jira_create`, `rick_jira_manage_links` (kept at 5: merging search-into-read and create-into-write would make their return shapes polymorphic, the documented kill-shot).
- **Confluence / observability** — `rick_confluence`, `rick_create_pr`, `rick_project_sync`.

## Files

- `server.go` — `Server`, `Tool`, `ToolDefinition`, `Deps`. JSON-RPC envelope types, `initialize` / `tools/list` / `tools/call` / `ping` dispatch, stdio `Serve(ctx, r, w)` loop with newline-delimited JSON framing (10 MiB buffer).
- `http.go` — `Server.ServeHTTP(ctx, addr)`. POST `/mcp` for JSON-RPC, GET `/mcp` for health/info, permissive CORS for the Wails webview. HTTP clients skip the `initialize` handshake (auto-marked initialized).
- `job.go` — `JobManager`, `Job`, `JobStatus`, `trackedJob`. In-memory async job registry with a background reaper (`maxJobAge = 2h`, `reaperTick = 5m`). Owns the lifecycle of `rick_consult` / `rick_run` subprocesses.
- `tools.go` — Registers only `rick_run_workflow` (which routes to `toolPlanBTU` when `dag=plan-btu`, folding the former `rick_plan_btu`). The other handlers that used to register here — `toolListWorkflows`, `toolListEvents`, `toolListDeadLetters` (now `rick_workflow_inspect` global panels), `toolInjectGuidance`, `toolApproveHint`, `toolRejectHint` (now `rick_workflow_control` actions), `toolPlanBTU`, plus the status/timeline/token/verdict/output reads and pause/resume/cancel verbs — all remain in this file as the implementation the facades dispatch to. Also defines shared `Deps`, the `register(Tool)` helper, `registerBuiltinTools()` (calls every group), and PR-URL/PR-source helper regexes (`extractPRURL`, `resolvePRBranch`).
- `tools_consolidated.go` — All facade tools (7). `rick_workflow_inspect` multiplexes per-workflow panels (status/timeline/tokens/verdicts/output/persona_output) when `workflow_id` is set and global panels (`list`/`events`/`dead_letters`) when it is not, via an `include` list; `workflow_id` is optional; per-panel failures (including "workflow_id required for panel X") surface under `result["errors"]` rather than failing the whole call; the `list` panel routes to `toolSearchWorkflows` when a ticket/source/repo/status filter is present, else `toolListWorkflows`. `rick_workflow_control` dispatches `action` ∈ pause/resume/cancel/retry/inject_guidance/approve_hint/reject_hint; reject's skip/fail decision is passed as `reject_action` and remapped onto the handler's `action` key by `remapRejectAction` (the discriminator would otherwise collide). `rick_diff_viewer` routes to a workspace diff on `workflow_id` or a PR diff on `repo`+`pr_number`. `rick_job_inspect` reads a job (status/output) when `job_id` is set or the global `list`/`backends` panels when not (`job_id` optional). `rick_wave_manager` dispatches `action` ∈ plan/launch/status/cleanup/pr_links. `rick_workspace` dispatches setup/cleanup/list; `rick_confluence` dispatches read/write. Each facade only dispatches to a handler defined in another file; it owns no business logic.
- `tools_jobs.go` — Direct AI execution tools (registers `rick_consult`, `rick_run`, `rick_job_cancel`). `rick_jobs` (list) and `rick_backends` are folded into `rick_job_inspect` (`list`/`backends` panels); their handlers `toolJobsList`/`toolBackends` remain here, as do `toolJobStatus`/`toolJobOutput` (the `status`/`output` panels). Backed by `JobManager` + `backend.Backend` subprocesses. No events. `toolBackends` reports the resolved default backend, the `RICK_REVIEW_BACKENDS` rotation, and per-backend whether the CLI binary is on PATH (`exec.LookPath`) — derived from `backend.Catalog` so it stays in sync with the factory.
- `tools_workspace.go` — `registerWorkspaceTools()` is an empty stub: the setup/cleanup/list verbs are the `rick_workspace` facade's `action`s (tools_consolidated.go), dispatching to the `toolWorkspace{Setup,Cleanup,List}` handlers retained here. Operate on `$RICK_REPOS_PATH` with a `*-rick-ws-*` deletion guard.
- `tools_jira.go` — Jira tools (5, consolidated from 12): `rick_jira_read` (ticket fields plus optional `include` joins for qa_steps / pr_links / epic_issues), `rick_jira_write` (field updates, comments, transitions, and custom fields like microservice in one schema), `rick_jira_manage_links` (create + delete issue links via an action), `rick_jira_create`, `rick_jira_search`. The pre-consolidation handlers (read-qa-steps, transition, comment, epic-issues, link/delete-link, set-microservice, pr-links) are folded into these. Requires `JIRA_URL` / `JIRA_EMAIL` / `JIRA_TOKEN` (resolved via `Deps.Jira`).
- `tools_wave.go` — Wave handlers. `registerWaveTools()` is an empty stub: the four wave lifecycle verbs (`plan` / `launch` / `status` / `cleanup`) AND the former `rick_github_pr_links` are all `rick_wave_manager` actions (the latter as `action=pr_links`, dispatched from `tools_consolidated.go`); their handlers `toolWavePlan` / `toolWaveLaunch` / `toolWaveStatus` / `toolWaveCleanup` / `toolGitHubPRLinks` live in this file unchanged. Everything below describes `rick_wave_manager action=plan` (formerly `rick_wave_plan`) and friends. Topologically sorts children of a parent work item and batch-launches workflows. Accepts three source kinds via a `source` discriminator: `{type:"jira", epic:"PROJ-X"}` (back-compat shorthand `epic:"PROJ-X"`), `{type:"github", parent:"owner/repo#N", child_discovery:"sub_issues"|"task_list"|"body_refs"|"auto", dependency_source:"table"|"body_refs"|"labels"|"none", allow_cross_repo:true, dag_options:{dag_map:{"rick:foo":"dag-name","default":"workspace-dev"}}}`, or `{type:"github", project:"owner/N", dependency_source:"project_field"|"body_refs"|"labels"|"none", dag_options:{...}}` for GitHub Projects V2 boards. GitHub parent-issue path structured into discovery (sub_issues API, parent-body task-list, parent-body refs, or `auto` which tries all three), dependency derivation (parent-body Depends-on table, per-child body keywords, `depends:<N>` labels, or none), and per-child DAG selection (rick:* labels → dag_map, then open-PR cross-reference via issue timeline → `pr-feedback`, then `dag_map["default"]` or `workspace-dev`). `allow_cross_repo` retains sub-issues/body-refs pointing at a different repo than the parent (each child is planned against its own repo). GitHub Projects V2 path reads every Issue item on the board (DraftIssue and PullRequest items recorded as `draft_item` / `is_pull_request` in diagnostics), cross-repo by default, and prefers a "Depends on" text field for dependencies (token needs `read:project`). Emits per-ticket `dag_params` so `rick_wave_manager action=launch` honors the plan's routing. Opt-in `RICK_GITHUB_GRAPHQL=1` env var collapses parent + sub-issues + timeline into a single GraphQL query; any error falls back to REST. Per-invocation `issueCache` dedupes `GetIssue` calls inside body_refs / task_list / body_refs-dependency modes. Status tracks merge-to-close: a GitHub child is marked `done=true` when its linked PR merged via timeline cross-reference, even if the issue is still open. `rick_wave_manager action=pr_links` mirrors `rick_jira_read`'s pr_links join — takes either a single `issue` or a wave source and returns cross-referenced PRs plus workflow correlation per child. Cleanup matches Jira children by key and GitHub children by `-gh<num>-` workspace suffix under `safeWorkspacePath`.
- `tools_observability.go` — Observability tools. Registers `rick_create_pr` and `rick_project_sync`. The former `rick_search_workflows` is folded into `rick_workflow_inspect`'s `list` panel (filtered) and `rick_retry_workflow` into `rick_workflow_control action=retry`; their handlers `toolSearchWorkflows`/`toolRetryWorkflow` remain here, as do `toolWorkflowOutput` / `toolDiff` / `toolPRDiff` (exposed via `rick_workflow_inspect` `output` panel and `rick_diff_viewer`). Reads tags/projections, drives `gh pr create`, emits Mermaid diagrams.
- `tools_confluence.go` — `registerConfluenceTools()` is an empty stub: read/write are the `rick_confluence` facade's `action`s, dispatching to `toolConfluence{Read,Write}` retained here. Requires `CONFLUENCE_URL` / `CONFLUENCE_EMAIL` / `CONFLUENCE_TOKEN` (resolved via `Deps.Confluence`).

Test files (`*_test.go`) cover protocol handshake, HTTP transport, job lifecycle, and per-tool behavior with mocked Jira/Confluence clients.

## Key types

- `Server` — holds `Deps`, the `tools` map, a logger, and a `JobManager`. Built once via `NewServer(deps, logger)`; tear down with `Close()` to stop the reaper.
- `Tool` / `ToolDefinition` — name, description, JSON Schema for input, and a `ToolHandler func(ctx, json.RawMessage) (any, error)` that returns a JSON-serializable result.
- `Deps` — injection bag: `eventstore.Store`, `eventbus.Bus`, `*engine.Engine`, four projections (`Workflows`, `Tokens`, `Timelines`, `Verdicts`), `SelectWorkflow`, `BackendName`, `WorkDir`, plus `backend.Backend`, `*jira.Client`, `*confluence.Client` for Tier 1-5 tools. (`rick_consult` / `rick_run` no longer read a server-wide yolo from `Deps`; they default `Yolo=true` per job via `resolveYolo`, opt-out with an explicit `yolo:false`.)
- `JobManager` / `Job` / `JobStatus` — async job tracking with `running`/`completed`/`failed`/`cancelled` states and per-job cancel funcs.
- `jsonRPCRequest` / `jsonRPCResponse` / `jsonRPCError` — wire envelopes, exported only within the package.

## Patterns

- **Tool registration**: each `tools_*.go` file owns a `registerXxxTools()` method on `*Server`. `registerBuiltinTools()` in `tools.go` calls all groups during `NewServer`. Adding a group means adding a single call there.
- **JSON Schema inline**: schemas are written as `map[string]any` literals next to each `register(Tool{...})` call — no struct tags, no codegen. Required fields go in `"required": []string{...}`.
- **Synchronous workflow tools vs async jobs**: workflow tools publish events through `Deps.Engine` / `Deps.Bus` and return immediately with a correlation ID; clients poll via `rick_workflow_inspect` (`status` panel). Job tools (`rick_consult`, `rick_run`) spawn a `backend.Backend` subprocess in a goroutine, return a job ID, and clients poll `rick_job_inspect`.
- **Facade vs handler**: the consolidated tools in `tools_consolidated.go` are pure dispatchers — they parse the multiplexing arg (`include` / `action`), forward the raw JSON to the relevant `tool*` handler, and (for `inspect`-style facades) fold per-panel errors into `result["errors"]` instead of failing the whole call. Never put business logic in a facade; it belongs in the handler the facade calls.
- **Env-gated tools**: Jira and Confluence tool groups expect `Deps.Jira` / `Deps.Confluence` to be non-nil. The wiring (`cmd/rick/serve.go`) only constructs these clients when the corresponding env vars are present; otherwise the tools are still registered but fail at call time with a clear error.
- **Result encoding**: handlers return any JSON-serializable value; `handleToolsCall` marshals it as pretty JSON inside a single `text` content block. Errors become `IsError: true` content blocks (not JSON-RPC errors) so MCP clients can render them.
- **Stdio framing**: line-delimited JSON, one request per line. HTTP framing is request-per-POST and bypasses the `initialize` handshake.

## Adding a new tool

1. Pick the right `tools_*.go` file (or add a new group + a `registerXxxTools()` method and call it from `registerBuiltinTools()` in `tools.go`).
2. Define the input args struct and (if useful) a result struct near the handler.
3. Inside `registerXxxTools()` call `s.register(Tool{Definition: ToolDefinition{Name, Description, InputSchema}, Handler: s.toolFoo})` — schema as `map[string]any`, with a `"required": []string{...}` slice if any args are mandatory.
4. Implement the handler `func (s *Server) toolFoo(ctx context.Context, args json.RawMessage) (any, error)`. Unmarshal into the args struct, talk to `s.deps.*`, return a JSON-serializable value or an error.
5. Add a test in the matching `*_test.go` (use the existing mock Jira/Confluence helpers if you need them) and update the tool count in the root `CLAUDE.md` and any agent-side surface (slash command list, autocomplete) if it should be operator-visible.

- `../workspace` — git/workspace primitives behind the workspace and wave tools.
